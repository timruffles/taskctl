# Installed-hook agent harness

Python 3 standard library only. This is a test harness, not a taskctl server or a native Codex client. It installs the actual JSON generated by `taskctl integrations codex config` for each test agent, runs the configured executable asynchronously on SessionStart/PostToolUse, and returns its context at the next tool-result boundary. Agents must read and explicitly ACK it. The harness never acknowledges on their behalf.

Build `bin/taskctl` first. Use a fresh absolute directory outside the source tree for disposable state:

```sh
go build -buildvcs=false -o bin/taskctl ./cmd/taskctl
python3 tests/agent_harness/setup_trial.py /absolute/trial
python3 tests/agent_harness/harness.py --root /absolute/trial serve
```

Run `serve` in a separate terminal/process. `TASKCTL_TEST_GO` may name a specific Go executable; otherwise setup uses Go from PATH. Setup creates isolated XDG directories and explicit project selection, and uses `examples/ledger` as the work directory. It does not delete an existing implementation; start from a copy containing only CONTRACT.md/go.mod when repeating the implementation exercise.

Install agent hooks and run every agent command through the wrapper:

```sh
python3 tests/agent_harness/harness.py --root /absolute/trial start --agent chaos-a
python3 tests/agent_harness/harness.py --root /absolute/trial run --agent chaos-a -- /absolute/taskctl/bin/taskctl tasks available --json
```

Use `chaos-a`, `chaos-b`, and `chaos-c` to match the setup subscriptions and CONTRACT.md. `run` returns JSON with the actual command exit, stdout, stderr and any hook_context. Check the embedded exit code. Supply edits as properly quoted command arguments. A shell sequence must not hide an earlier failed command behind a later successful one.

The demonstration uses a 20-second inactivity threshold and initially 10-second delivery leases to expose failures quickly. Normal taskctl defaults remain 30 minutes and five minutes. After delayed/duplicate notification tests, use five-minute leases in the installed hook configurations to drain final notifications without artificial timing pressure.

## Fault controls

`fault --agent NAME --kind KIND [--value VALUE] [--count N]` supports:

| Kind | Effect |
| --- | --- |
| drop_command_response | Hide the next successful command result after it commits; return unknown outcome |
| drop_context | Drop a nonempty hook response after its delivery offer commits |
| delay_context | Delay context by VALUE seconds |
| duplicate_context | Deliver a second copy, optionally delayed by VALUE seconds |
| delay_hook | Delay hook execution by VALUE seconds |
| skip_hook | Skip one hook invocation |

Use `crash --agent NAME` alongside interruption of the actual agent runtime. The server signals only live command processes it owns, revokes new execution for that identity, and records the action. A fresh `start` explicitly resumes the identity. The harness is cooperative test infrastructure, not a security sandbox against a process that can edit its database or impersonate another identity.

`service-crash` waits for active commands to finish and SIGKILLs the server itself. Restart `serve`: pending hooks replay, and any command interrupted during another kind of server failure is reported as unknown outcome. The harness does not blindly retry arbitrary commands. For create retries use the same taskctl `--request-id` and input.

`drain --agent NAME` is nonblocking. `status` shows execution state. `export --file /absolute/evidence.json` saves commands, hook jobs, fault receipts and audit records. Create `stop-server` inside the trial directory for graceful shutdown. Do not run two servers for one trial directory.

After agents finish, `verify_demo.py /absolute/trial` builds the demo and verifies 22 real CLI fixtures. The taskctl state-machine, storage and notification chaos tests are independent Go tests; see `docs/CHAOS_VALIDATION.md`.
